# Documentation audiences

Choose the reader and keep one current account. Link to details instead of
copying them. Existing layouts may combine related material; do not create a
file for every paragraph.

| Location | Reader and purpose |
| --- | --- |
| Workspace README and operating guides | Owner: using this workspace |
| Project MAINTAINER.md | Owner: release steps and useful local findings |
| AGENTS.md | Agents: edit boundaries and required behavior |
| Project README, PURPOSE.md and About/About.xml | Players: behavior, controls, dependencies and meaningful limits; PURPOSE also guides contributors |
| CHANGELOG.md | Users: changes by version; retain upstream history |
| DESIGN.md, BUILDING.md and provenance | Contributors and agents: implementation, costs, source origins and useful checks |
| Investigations and saved reports | Owner and developers: substantive diagnoses, measurements and open questions |

Write current conclusions and non-obvious reasons. Replace superseded status;
do not append task histories, conversation transcripts, routine successful
commands, corrected fixture mistakes or repeated isolation assurances. Keep a
failed approach only when it prevents likely repeated work. Routine edits need
no investigation document, validation diary or saved report.

Use current dependencies. Record versions or upstream commits when they explain
a finding; omit assembly hash inventories. Briefly state useful check results
and material limits, with evidence links when worth retaining. Do not imply a
complete gameplay route was tested by a helper fixture. Performance claims must
match evidence; document one-time initialization and recurring work costs.

Player copy describes what players set and what pawns do, using native vocabulary
and exact control labels. Keep technical configuration in settings and code
details in developer docs. Omit task narration, internal status, generic praise
and objections nobody raised. Missing initial data is not an error; never invent
measurements. Keep requirements, real limits, predecessor links, credits and licenses.

When controls or advertised behavior change, update the source description and
public docs together. Refilled uses About/About.xml for both the mod list and
Workshop description; plain URLs work in both. Check predecessor names and links
when changing them. Publication is a separate action; record its state only when
checked and useful for release work.
